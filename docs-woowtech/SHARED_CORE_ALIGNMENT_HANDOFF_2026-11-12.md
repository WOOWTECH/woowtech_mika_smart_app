# 渥屋助理 GitHub 版與商店版：共用功能對齊交接

日期：2026-11-12。此文件是執行計畫；不是修正完成或發布紀錄。

## 目標與已確認的產品範圍

對齊兩版共同提供的外部 MCP、個人技能與結果評分，讓相同設定下的行為一致。GitHub 版保留原有能力；商店版依使用者先前決定保留對話、語音、瀏覽器、記憶、技能與外部 MCP，不恢復跨 App 手機操控、手機對電腦的 MCP 服務或遠端配對。兩版套件名稱、簽章與本機資料各自獨立，不假設設定會自動同步。

任務授權包含原始碼修正、建立測試、使用本機測試伺服器、建置及已授權的 POCO 實測。此文件不宣稱已授權發布新版、送審或在真實 HA 家電執行寫入。真實 HA 驗收預設只讀；若要測寫入，使用專用可清理的測試資源。

## 接手前先確認現況

1. 更新並記錄 GitHub 主線與商店分支的實際 commit、工作樹狀態、POCO 連線及兩個已安裝版本。檢查現有未提交變更與既有交接，避免覆蓋別人的工作。本文的基準是 `origin/main` `05bce637`、`playstore/woowtech-compliant-20261111` `44ec0cba`，後續有新提交時以新基準重新比對。
2. 商店版參考提交：`20df66fc` 含 MCP 合成工具清單檢查，`af6df39b` 加入專用長結果讀取，`9d0948ca` 修正技能評分。這些提交也改動商店版任務接線；**不要整批 cherry-pick 覆蓋 GitHub 版的手機操控或商店版功能邊界**。逐個抽取共用變更、保留兩版差異，或在獨立共同基底實作後分別移植。
3. GitHub 版此前 POCO 使用 `WOOW` 模型時顯示請求太頻繁；商店版使用 ChatGPT `gpt-6-sol` 的結果已通過。不要把不同模型的結果當作兩版能力差異。測試若需登入同一可用模型，保留現有設定並使用者協助登入；不要複製、記錄或提交憑證。
4. **更正先前對照結論：**GitHub 版沒有商店版的 `mcp_local_results__read`，但它的 `ConversationMcpResultStore` 已儲存到對話工作區，GitHub 版主任務亦帶沙箱 `read_file`。它可能已能讀取後段，尚需實測。先判斷既有路徑是否可用、是否符合需求，再決定是否加入專用讀取器；不要把「工具名稱不同」當成已證實讀不到資料。
5. MCP 設定目前 `allowedTools=null` 表示不限制；編輯器空白也存成 null，無法用空白表示拒絕全部。現有介面是逗號分隔名稱，不能假定已有工具勾選介面。保留既有清單及空白的實際語義；新設計若區分「全部」「指定」「全部停用」，要規劃設定版本、遷移及清楚顯示，不能把既有 null 靜默改成拒絕全部或反過來。

## 一、MCP 清單與執行權限

**問題：**GitHub 版的 `McpClient` 對伺服器工具有清單過濾，但合成的 `resource_read`、`prompt_get` 在特定情況未套用相同檢查。商店版 `20df66fc` 已補組裝階段檢查，尚需確認執行期間的設定變更及舊設定相容性。

1. 比對 `core/.../cap/mcp/McpClient.kt`、`app/.../settings/McpServerStore.kt`、`app/.../ui/McpServersScreen.kt`。為工具、資源與提示建立一致、明確的權限決策；檢查伺服器本身工具與合成工具同名時的行為，不能因名稱碰撞繞過限制。
2. 列給模型時執行過濾，並設計呼叫時核對目前設定。若現有架構將清單快照固定於任務開始，需增加安全的動態查詢或在設定變動時終止／重建受影響連線，確保撤銷後下一次呼叫被拒；已開始的呼叫如何處理必須如實顯示與測試。
3. 維持每伺服器獨立設定；設計 `resource_read` 的權限範圍時，明確告訴使用者它可能讀取該伺服器的多個資源。伺服器聲稱唯讀只作參考，原有高風險工具確認流程仍需生效。不要在清單過濾中繞過原有審批及來源信任規則。
4. 舊設定遷移需覆蓋 null、明確清單、空集合、編輯再儲存、重新啟動與伺服器工具新增／刪除。保留既有 null 的「不限制」意義並清楚提示；如新增「拒絕全部」狀態，須可持久化且與空白舊資料區分。若無法安全、明確遷移，先交付向後相容的合成工具修正，將 UI 重設計獨立處理。
5. 優先使用可重現的本機 MCP 伺服器，提供一般工具、resources、prompts、同名與動態清單；驗證允許、未允許、撤銷及重啟的實際呼叫。HA 實機採只讀工具，避免控制真實設備。

## 二、個人技能結果與誤停用

**現況：**商店版 `9d0948ca` 將成功工具名稱提供 `OutcomeJudge`，並調整 `SkillOutcomes` 的試用技能處置；POCO 已有一次 `skill_read` 成功、`outcome=done`、技能轉正式的真實模型重測。GitHub 版仍是舊邏輯。

1. 將必要的 `OutcomeJudge`、提示詞、`TaskRun.settleOutcome`、`SkillOutcomes` 及對應測試以共用小變更移入兩版；保持背景評分不阻擋使用者看到回答，失敗／逾時維持未知狀態。
2. 明確區分「成功呼叫技能工具」「實際讀取的是哪個技能」「任務最終是否完成」。現有修正只傳成功工具名稱，**不能單憑工具名證明特定技能已被使用，也不能單憑讀取判定任務成功**；若要作技能級狀態轉換，先確認現有事件能否可靠關聯技能 ID，避免傳入工具輸出、憑證或過多個資。
3. 模型限流、斷線、取消、事件缺失或判定未知，不得被當成技能故障直接停用；真正可歸因的核查失敗仍需按產品規則處理。驗證既有正式技能與歷史狀態的行為，並提供現有停用技能的手動恢復；不要批次自動恢復使用者曾主動停用的技能。
4. 不得把模型評分本身當成不可逆操作的授權；原有付款、發布等確認仍需保留。

## 三、MCP 長結果的讀取與資料生命週期

1. 先在 GitHub 版驗證：MCP 工具產生超過預覽長度的結果 → `fullResult` 指向本對話 → 模型或受控測試呼叫沙箱 `read_file` → 讀取後段並回覆。沙箱不可用、沒有工作區或遠端來源任務等情況分別記錄，避免以單一主流程推定全部可用。
2. 商店版既有 `ConversationMcpResultReader` 是只讀本對話 `mcp-results/` 的專用工具，單次最多 3,000 個字元；目前檔案超過 4,000,000 bytes 回 `result_too_large_to_read`，且每次讀取會先載入整個檔案。GitHub 的 `read_file` 使用位元組 offset，專用工具使用字元 offset；測試繁中、emoji 與跨段內容，勿直接套用對方 offset。
3. 若 GitHub 既有 `read_file` 已通過，保留可用性並評估是否為一致提示、受限權限或無沙箱場景共用專用讀取器。若採共用讀取器，兩版要共用其契約與測試，並檢查是否與 GitHub 既有 `read_file` 重複暴露及產生模型選擇混淆。
4. 限制結果存取於本對話；拒絕其他對話、路徑穿越、符號連結及偽造檔名。結果按不可信外部資料處理，不能把其中指令當系統命令；不把完整敏感結果或憑證寫入日誌。
5. 檢查寫入失敗、檔案不存在、超限與清除；要明示未讀完整，不能把摘要冒充完整答案。評估流式／有界讀取以免大檔重複載入耗盡記憶體，必要時維持明確上限。核對刪除對話時實際清除結果的行為，補上測試與必要修正；不假設現有清理已完成。

## 四、測試與驗收

先執行受影響核心測試：`OutcomeJudgeTest`、`SkillOutcomesTest`、`McpClientTest`，以及新增的長結果和任務接線測試。現有專案曾無 `:app:testWoowtechDebugUnitTest` 任務，先用 Gradle 列出實際任務；需要 Android 環境的案例用可執行的裝置測試。再依分支實際建置配置編譯 GitHub 版、商店版 Debug 與商店版 Release AAB，檢查商店版 Manifest 與能力邊界。測試與建置失敗要記錄原始原因，不得算通過。

兩版在同一可用模型及相同設定下，於 POCO 分別實測並記錄版本、時間、測試步驟與執行證據：

| 驗收 | 必要案例 |
| --- | --- |
| MCP 清單 | 空／舊設定遷移、指定四項、resources／prompts 未授權及明確授權、呼叫前撤銷、同名、重啟與不同伺服器隔離；確認實際呼叫與顯示一致。 |
| 技能 | 試用技能讀取後完成、讀取後失敗、未讀取、模型限流／取消／未知、明確核查失敗、正式技能及手動恢復；不得因未知誤停用。 |
| 長結果 | 短結果、跨預覽後段、繁中與 emoji、跨段與結尾、檔案不存在、超過限制、不同對話與越界路徑、刪對話後清理。GitHub 先測既有 `read_file`，商店版測專用讀取工具。 |
| 安全與相容 | HA 唯讀 `ha_get_state`／總覽；測試工具寫入僅限本機或專用虛擬資源；原有確認與兩版功能邊界不回歸。 |
| 基本回歸 | 對話、記憶跨對話、技能設定、MCP 設定儲存、瀏覽器及既有語音流程；人聲需真人實測，不以自動化代替。 |

測試產生的對話、技能、記憶與虛擬設備應逐項清理並確認；保留使用者原有帳號、配對與資料。若設備被其他人使用、模型限流或需真人操作，記錄阻礙與已完成部分，不能宣稱全面通過。
