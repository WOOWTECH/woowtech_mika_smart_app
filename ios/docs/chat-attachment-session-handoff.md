# One-shot general attachment session integration

`ChatSession` now exposes its own `attachmentPresenter` to a future composer host; `ContentView.swift` is deliberately unchanged. The existing picker can be initialized once with `ChatAttachmentPickerViewModel(presenter: session.attachmentPresenter)`. The host must observe both the view model's state and the session when deciding whether the send button is enabled; presenter changes do not themselves publish through `ChatSession`. The host calls `session.send()` and must never call `takeConfirmed` itself.

Before showing or refreshing the review, call `prepareAttachmentReview(vision:)`. The default is `.unknown`; `.supported` is an explicit host declaration for this exact endpoint and model, not a guess from its name or a successful text test. No existing saved model setting declares vision capability, so production image selection remains blocked until a later UI/configuration supplies an explicit, defensible declaration. The service can still reject an image. `.unsupported` and `.unknown` both block image confirmation; UTF-8 text does not require vision. The session binds the declaration, endpoint, model, credential account, draft, quoted source, history and learning/skill snapshot to the review. It validates the exact reviewed context and rechecks live inputs and key after the async handoff, immediately before initiating the model client.

This first integration sends one selected image or bounded text attachment in one ordinary complete or streaming model request. It intentionally rejects attachment requests while MCP or the memory master switch is enabled: their tool flows can make several model requests and the existing protocol would otherwise replay the attachment or expose it as tool authority. Existing text-only tool, MCP, memory and automatic extraction flows are unchanged. Approved skill guidance can still accompany the attachment and is disclosed in the review. Neither file contents nor model output are fed into automatic memory extraction by this attachment path. There is no implicit retry or streaming fallback for an attachment.

The full attachment is sent to the reviewed model service. The encrypted archive stores the ordinary completed user prompt and answer using the existing versioned archive; the original attachment, selected URL and filename are not inserted into it. **The model's answer can itself contain attachment-derived content and remains eligible for normal archive, quoting, branching and later conversation history.** Later history can therefore send those answer excerpts again. The review explicitly states this boundary. Filenames, destination URLs, answers, and quoted text can all contain personal data; never log them or the attachment bytes.

On failure, cancellation or timeout, the text draft and quote stay in place. Once the attachment has been taken, it cannot be replayed: the host displays `attachmentIssue` using `AppLocalizer` and offers explicit reselection and confirmation, or `discardGeneralAttachment()` to proceed without the attachment. A failed selection also blocks accidental text-only send until reselected or explicitly removed. Server receipt may be unknown even when a request fails. The host disables picker changes during submission and calls `generalAttachmentEnteredBackground()` on backgrounding. The existing new-conversation confirmation does not yet present a general-attachment prompt; the future composer must inspect `session.hasGeneralAttachment` and provide that explicit decision. It must obtain the user's explicit decision before calling `discardGeneralAttachment()` for navigation, and arrange that before opening/creating another conversation; `openConversation`, `newConversation`, deleting the current conversation, branch preparation and PDF selection protect pending general attachments. The host must refresh the review after draft, quote, settings, tool or reference changes.

`python3 ios/scripts/check_chat_attachment_session.py` snapshots and compiles real session sources for Debug and Release with local fake model clients, isolated stores and generated files. It exercises plain/streaming success, image declaration, cancellations, failures, source/destination changes, and v5 branch/quote persistence without a real account or model. iOS SDK compilation, the system picker, third-party providers, the eventual composer lifecycle and real model compatibility still require native validation on a Mac with Xcode.

## Attachment selection failures and archive concurrency

A picker/import failure remains a pending decision when the draft, destination or review context changes. A successful replacement selection or explicit removal resolves it; an edit cannot silently turn the request into a text-only send.

For an archive-backed attachment request, the session acquires the same advisory cross-process vault lock used by cooperating archive stores, reloads the encrypted archive inside it, and compares the exact current conversation and quote-source snapshots with the reviewed values. A missing, changed, unreadable or locked archive prevents the model call. The lease remains held through client execution rather than being released after the reread: this closes the interval in which another cooperating store could delete the reviewed history before the model client starts. All conversation archive operations now try the lock without waiting, so an operation against the same vault, including an unrelated conversation, can fail while an attachment request is running; retry after it ends. The lock is advisory and cannot constrain an external writer that bypasses the vault protocol.

A completed client call releases the lease before saving the answer, whose normal optimistic conflict checks still apply. On cancellation or failure the lease is retained until the client actually returns. For streaming, consumer cancellation alone is not proof that the producer has stopped: `HTTPChatModelClient` explicitly retains the lease in its worker until that worker ends. Attachment clients must explicitly guarantee that their complete operation does not return while request-starting work is still alive; other clients are rejected before consuming the attachment. A streaming client whose complete path has that guarantee but whose streaming producer lacks the separate lifetime contract is selected for one complete request instead; no failed stream is retried. A non-cooperative client/producer that never returns can retain the lease indefinitely, making archive operations fail until it ends or the process exits. The real HTTP client has bounded transport and cancellation, but a server may already have received a request at cancellation. No lock can retract data already sent or prevent a writer that ignores the lock.

The offline regression starts a second archive store with the same encrypted vault, deterministically deletes after review but before lease acquisition, attempts deletion at the client-start probe, and holds complete and streaming producers across cancellation. The selected-file-error regression edits the draft before removal. These are local tests; they do not verify the iOS system picker, a real account, or a model service.
