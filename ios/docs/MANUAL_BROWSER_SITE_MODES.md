# Manual website display preferences

This change was reviewed against Mika and integrated onto the iOS mainline after `c7cdfbd`. It does not establish full Mika browser parity.

Reference inspected at `/tmp/woow-mika-memory-reference`, revision `0c172724f3f0c96f7345262588072f6e95db1138`:

- `app/src/main/java/com/wangzan101/mika/browser/BrowserIdentity.kt`: `BrowserIdentity` and `UserSiteModes`.
- `app/src/main/java/com/wangzan101/mika/browser/UserBrowser.kt`: `setDesktop`, `createTab`, and manual mode policy installation.
- `app/src/main/java/com/wangzan101/mika/cap/web/cdp/SiteModes.kt` and `WebDevtools.kt`: separate agent preferences and `agentWantsMobile`.

Manual navigation defaults to mobile. A user can save desktop or mobile in the browser toolbar's website display menu. Desktop hostnames inherit to subdomains, normalize case, trailing dots and one `www.` prefix, and compare at label boundaries. Switching a child to mobile removes matching ancestor desktop entries. Independently saved siblings and descendants remain desktop, as in Mika. The set is bounded to 500 valid hostnames; capacity/invalid-input failures leave state intact. Public IP literals and IDNA ASCII hostnames are accepted under the existing URL policy.

The choice is saved in the existing AES-GCM browser-library vault, with the production Keychain key, file protection and backup exclusion unchanged. The additive `userSiteModes` field retains schema version 1. A missing field in an old vault defaults to mobile and preserves tabs, selection, bookmarks and history. A present malformed/null field or corrupt ciphertext fails closed. State is published only after successful persistence. An older app can decode the added field, but saving from an older app can discard that field; downgrade round-trip preservation is not promised.

An explicit mode change immediately reloads the selected tab once when the current manual document has verified GET method evidence. The actual `WKNavigationAction.request.httpMethod` must be exactly GET, with no body/stream, on an allowed manual main-frame action. `BrowserSiteModeReloadState` binds that action to the next uncontested navigation start (and the exact app-issued navigation object when available), then requires the same retained `WKNavigation` object and URL at commit and finish. Only that finished document can authorize reload. The evidence is ephemeral and cannot survive restoration or be inferred from URL equality alone.

POST/non-GET, unknown method, automation ownership, redirects, overlapping actions, cancellation, failure and process termination cannot authorize immediate application. The gate is consumed before one `WKWebView.reload()` call; the navigation delegate additionally rejects any non-GET/body-bearing main-frame request during that reload. Redirects are conservatively deferred on later mode changes because their final method is not inferred from a URL-only redirect callback. No automatic retry occurs. Only the selected tab reloads; inherited changes in background tabs wait for their next navigation.

The UI reports either “網站偏好已儲存，正在重新整理此頁以套用。” or the explicit deferred behavior: “網站偏好已儲存；為避免重送表單或自動化操作，此頁不會重新整理，下次手動導覽時套用。” Pending proposals and dialogs in affected sessions are cancelled. The WebView/data store is retained, preserving cookies, tabs and the download manager. A verified GET reload replaces the current document (including unsaved fields); POST/unknown/automation pages retain their document. The change never releases automation ownership. The control is unavailable during active work, navigation, website-data clearing or unavailable storage.

The new preferences navigation delegate routes through the same existing URL, method, origin and download policy as the old delegate. Only allowed main-frame manual navigation receives `.mobile` or `.desktop`. Subframe preferences are left alone. Automated navigation retains the existing `.recommended` policy; this change does not add Mika's separate agent desktop/mobile database or its login-for-agent identity behavior.

Apple documents that the preferences delegate replaces the older action-policy callback, and that content-mode preferences are ignored for subframes: [navigation preferences delegate](https://developer.apple.com/documentation/webkit/wknavigationdelegate/webview(_:decidepolicyfor:preferences:decisionhandler:)), [preferredContentMode](https://developer.apple.com/documentation/webkit/wkwebpagepreferences/preferredcontentmode). The test reads effective mode from the committed **WKNavigation**, as documented in [effectiveContentMode](https://developer.apple.com/documentation/webkit/wknavigation/effectivecontentmode) and [Apple's desktop browsing example](https://developer.apple.com/videos/play/wwdc2019/203/). There is no custom user agent, viewport injection, arbitrary production JavaScript, or URL-policy exception.

Run local validation with `python3 scripts/check_browser_site_modes_app.py`. It snapshots and hashes the actual sources, compiles Debug and Release App code against macOS WebKit, and executes the shared core checks plus the real workspace/WebKit harness. Every run prints its report directory. Files and encryption keys are synthetic and isolated; keys stay in memory. WebKit uses a nonpersistent profile. Controlled HTML responses use Apple's public [`loadSimulatedRequest(_:responseHTML:)`](https://developer.apple.com/documentation/webkit/wkwebview/loadsimulatedrequest(_:responsehtml:)) API and reserved HTTPS URLs. In those workspace tests, reload/link/form/frame/download actions are intercepted after the production policy decision. A separate Debug process uses the existing gated loopback HTTP fixture to verify a completed reload. Production URL policy and the existing fixture gate are unchanged.

Coverage includes hostname normalization/inheritance/bounds, legacy schema and encrypted legacy migration, encrypted restart, failed writes and corruption, actual preferences callbacks, unchanged subframe preferences, proposal cancellation/rejection, cookie retention, separate agent defaults, private/cross-origin/query/POST/download restrictions, manual download authorization and new-tab wiring. Pure reload-state checks cover exact navigation identity, commit/finish ordering, missing/unknown methods, bodies, POST after GET at the same URL, overlap, redirects and stale callbacks after cancellation.

The Debug and Release workspace tests each assert that saving a changed preference issues one actual GET `.reload` action with the desktop preference, cancels a pending proposal and retains the WebView/cookie store. That action is intercepted because a simulated response cannot serve a subsequent network reload. A real WebKit POST navigation loaded with a controlled simulated response commits and finishes at the same URL as the earlier GET; changing mode produces zero new actions/finishes and preserves its edited field. A real new document with a deliberately omitted policy observation also produces no reload and shows the deferred notice. Automation-owned documents remain deferred.

The separate Debug HTTP test uses the existing `BrowserLoginFixture` with a unique namespace and nonpersistent WebKit profile. After a fixed synthetic fixture login, an explicit manual GET establishes method evidence. Changing mode calls the actual production `WKWebView.reload()` path: the test observes exactly one GET `.reload` action and one additional finish, a different navigation object, the desktop preference and the same WebView. The server's protected-page counter advances by exactly one and authenticates the retained HttpOnly cookie; its login POST counter stays at one. A completed HTTP POST response without a redirect then remains unchanged when the mode changes, with zero new navigation actions/finishes. A POST/redirect chain is also deferred. This HTTP test injects the mode resolver directly because the production hostname store correctly rejects loopback; encrypted persistence and the workspace setter are covered separately by the reserved-HTTPS tests. No personal credentials, personal browser profile or external service is used. No active download transfer is exercised.

On macOS 13.7.8 / Swift 5.8.1 CLT, `WKNavigation.effectiveContentMode` reported `.recommended` for both requests in the local run. Receiving the preferences callback does not prove iOS rendering behavior. `swift test` cannot run on this host because CLT cannot resolve the SDK PlatformPath. iOS syntax parsing is reported separately and is **not** native typechecking, XCTest execution or UI acceptance.
