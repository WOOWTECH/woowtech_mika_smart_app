# Architecture decision record — iOS assistant

## Product boundary

The target scope is model conversations, memory, file work, controlled MCP connections, declarative skills, WebKit browsing, notifications, language and appearance. Not all are implemented; see the verification log. It never controls other iPhone apps, uses Accessibility to automate the device, records the screen, runs ADB, or executes arbitrary local programs.

## Modules

`AssistantContracts` owns Codable messages shared with the future gateway. `AssistantDomain` owns run state without UI dependencies. `AssistantBrowser` owns URL policy, research/website/route state, DOM approval validation and a fixed isolated-world WebKit adapter. `AssistantModels` owns JSON/SSE networking; `AssistantMCP` owns Streamable HTTP and a bounded model conversation runner. Memory, Skills and encrypted persistence have separate modules. The app target owns SwiftUI, foreground sessions, settings and device-only Keychain adapters.

## Browser modes

`local_webkit` is the only default mode. Its cookies and login data remain in the app's WebKit data store. `remote_browser` is a later, opt-in server capability for CDP-grade automation; it never receives local cookies, passwords, OTPs or Passkeys automatically.

## Implemented execution boundaries

Like the Android direct-download edition (1.1, 2026-11-18), several MCP servers can be saved, each with a name, an on/off switch, its own endpoint, optional access token and tool choice. Everything MCP keeps lives in one Keychain service (`MCPKeychainItems`): the server list (account `servers`) and each server's accounts (`server.<id>.endpoint`, `.token`, `.allowed-tools`); the server of the single-server version keeps its original `endpoint`, `token` and `allowed-tools` accounts and becomes the first entry the first time the list is read, so nothing is copied. Deleting a server removes only its own accounts, then its entry; `FreshInstallKeychainReset` removes the whole service, so every server goes after a reinstall. Nothing of it is in UserDefaults or logs. There is no per-chat switch: every request connects the enabled servers at once and waits for them together at most 15 seconds (Android `CONNECT_BUDGET_MS`); a server that fails or is still connecting is left out of that request and named above the chat, and a connection that finishes later stays for the next request. The tools of every connected server form one catalog (`MCPCombinedCatalog`) named like Android's `mcpToolNames`: `mcp_<server>__<tool>`, with a digest form past 64 characters, so two servers may offer the same tool name; iOS passes the first eight hex digits of the server's id (kept unique among saved servers) where Android passes the whole id. Each tool's description starts with Android's provenance line naming the server; a resource URI two servers share is told apart as `mcp_<server>:<uri>`. Each call goes to the server that owns it under its own name, and is checked again just before it is sent: the same connection, the tool still selected (Android `isAllowedNow`). Every usable tool starts allowed, up to 256 tools and 224 KB a server; all servers together stay within the runner's 256 tools and 256 KB, in server order, and the chat says how many were left out. A plain or memory chat offers that catalog with its skill and web task offers; a reply that is exactly one `call_tool` or `read_resource` starts the MCP step (`MCPConversationRunner` with an `MCPConversationEntry`), which runs that command first. A memory chat's earlier memory search or one change goes along and counts toward the step's one search and one change. The MCP step can end with a web task or a skill tool (`MCPConversationHandoff`): nothing of it runs in the runner, and the next step receives the MCP commands and results so far (at most 48 KB, newest kept). Plain answers still stream. In the background iOS stops a running MCP step (已停止。) and the connections; a request whose MCP command arrives after that, or after a server changed, starts nothing (`MCPChatChanged`). A plain reply, a web task or a skill step keeps running as before. Like the Play build, up to 30 resources a server lists are offered read-only without a picker; server prompts are not offered. There is no per-call approval: the tool selection is the limit, and each call, its server and its result are listed in the chat's results view.

Browser research remains read-only. The separate interaction entry point observes stable document/node IDs, asks the model for one action, and waits for a native review. A one-use grant expires after 60 seconds. Before dispatch, fixed JavaScript checks document/snapshot identity, the actual node reference and its captured attributes/form values. All values cross the WebKit argument bridge; no model-supplied JavaScript runs. DOM events are synthetic; dispatch is not proof of a completed website task. Interaction traces are not automatically treated as read-only routes or successful skill-learning evidence.

A server can sign in with OAuth 2.1 instead of a fixed token (Settings › MCP 伺服器 › 驗證方式 › OAuth 登入, like Android's `McpOAuth.kt`; `MCPOAuth` in AssistantMCP). Discovery follows the MCP spec's order: the `resource_metadata` of the 401 an unauthenticated `initialize` gets, then `/.well-known/oauth-protected-resource` with the endpoint's path, then at the root; the authorization server's metadata is tried with RFC 8414 path insertion, OpenID path insertion, then OpenID after the issuer's path, and a document counts only when its `issuer` is the one its address was built from, one trailing slash aside (RFC 8414 §3.3), so an MCP host's own metadata never stands in for the authorization server its resource metadata names. Only a 200 answer counts and no redirect is followed. Every discovery and OAuth address must be HTTPS, loopback included; only the checks' own client, through an internal opt-in the App never sets, reaches their fake servers over HTTP on 127.0.0.1. The App registers itself (RFC 7591, public client `woowtech agent`, the loopback redirect) or, when the server registers no apps, uses a client the user registered and entered under 進階. The authorize page opens in ASWebAuthenticationSession and comes back to `LoopbackCallbackServer`, as for ChatGPT; the request carries PKCE S256, `state`, the scope (the challenge's, else `scopes_supported`) and `resource` (RFC 8707: the resource metadata's, else the endpoint without its query), and an `iss` is checked (RFC 9207). The sign-in is one JSON item per server (account `<prefix>oauth`, ThisDeviceOnly) in the MCP service, so deleting the server or a fresh install removes it. Connections get the token from `MCPOAuth.tokenGate` (`ModelAccountTokenGate`): refreshed a minute before expiry, rotated refresh tokens saved; a 401 is refreshed once and the request sent once more, and a dead or refused sign-in shows 需要重新登入 on the server instead of a connection failure. 登出 clears this device only. Not done: Client ID Metadata Documents, step-up authorization after a 403 `insufficient_scope`, and revoking tokens on sign-out. `scripts/check_mcp_oauth.py` checks it against fake servers.

Chat turns follow the Play build (since 2026-11-14). The question enters the transcript and the input bar empties when it is sent; a working row (spinner, 正在處理, elapsed time) stands in until the reply streams. A turn ends as an answer, as 沒有完成 with its reason, or as 已停止。; all three are saved with the conversation (archive v6, `ArchivedConversationTurn.outcome`), and only answered turns go back to the model as history. Ordinary chat has no fixed time limit (MCP runs keep their 180-second host deadline). A conversation is not tied to the model it was saved with: changing the main model keeps the open conversation, any saved conversation opens from the drawer and continues on the current main model, and its row keeps the model of its latest turn. One encrypted archive file holds up to 200 conversations of up to 1000 turns and 8 MiB; when a save would pass a bound, the oldest unpinned conversations give way (their attachment files with them) instead of the save failing.

The bundled skill catalog stays a pinned, hash-checked archive of the original documents and scripts. Like the Play build (since 2026-11-14) the App has no catalog page, skill-writing pages or PDF runtime; the archive supplies the upstream LICENSE and NOTICE for Settings › About. Remote gateway, full original-skill tool registration, provider-native function-call streaming and full browser parity remain unfinished.

- Credentials belong in Keychain, never SwiftData, logs or chat content.
- iOS keeps Keychain items after the App is deleted. `FreshInstallKeychainReset` removes the production services on the first launch of a fresh install (no marker, App defaults or App files) and keeps them on an upgrade, whose encrypted files need their keys. A new production Keychain service must join its list.
- MCP is an outbound client. Server annotations and descriptions never authorize calls; the remote server validates its input schema. A server signs in with nothing, a manual Bearer access token or an OAuth 2.1 sign-in; stdio and legacy SSE remain unsupported.
- Skills are reviewed text context, not local executable programs. Optional remote computation must be distinguished from iOS capabilities.
- Approval is bound to the current immutable operation and run. Neither a model answer nor a saved JSON boolean is an approval credential.


## Browser workspace and files

BrowserWorkspace owns one persistent WebKit profile and a separate BrowserSession/WKWebView per live tab. Metadata is encrypted with a dedicated device Keychain key; known callback/secret URLs are excluded. Manual HTTPS navigation accepts login/query URLs while model research retains its existing public-page restrictions. Switching/closing tabs revokes pending proposals. Website-record removal first quiesces every old document, then removes the selected records; history/bookmarks and learning data have separate deletion controls.

Like the Play build (since 2026-11-14) the browser refuses downloads with 「瀏覽器裡暫時不能下載檔案。」. Native WebKit file inputs use the system chooser on iOS 17. DEBUG upload fixtures permit only an exact loopback origin/path; the loopback ATS exception is in the Debug plist only. Release builds have no fixture server or ATS exception.
