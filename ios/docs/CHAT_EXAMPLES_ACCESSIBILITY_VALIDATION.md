# Chat example accessibility candidate

The Android Play-flavor reference is source `420b1d26f99110635d6a2827ee9414541c7a6c35`: `EmptyState` lays out six full-text button rows in the conversation list; each row replaces the draft without sending. This candidate retains that behavior and makes the iOS examples scale with Dynamic Type. Empty-state geometry no longer invokes transcript tail following. The model, file, browsing and memory capabilities are not established by these examples.

The supplied Craft Anything evidence is preserved in [`evidence/craft-play-420b1d26-chat.json`](evidence/craft-play-420b1d26-chat.json). It identifies the unsigned arm64 Release candidate from CI run `43183040946` (artifact SHA-256 `a53e5386811b8c3df3a8d70164c3c984188afe71329b5671d4595bd7432fc50c`) and records the same six Traditional Chinese strings. This is a static resource inspection, not a Play-distributed APK, a runtime UI observation, or a functional model test.

The simulator UI method is `WoowAssistantUITests/WoowAssistantUITests/testStoreExamplesRemainScrollableAndAccessibleAtLargestText`, owned by `ui-startup`. Run on the iOS 18.5 iPhone SE (3rd generation) configuration, with the usual isolated UI test namespace and no live flags. The DEBUG/simulator-only `-UITestChatAccessibilitySize` fixture requires `-UITestMode` and a UUID namespace; it sets the SwiftUI environment to `.accessibility5` for this process. Release and ordinary launches do not use the fixture. This simulates the largest SwiftUI size; it is not a test of the system Settings control.

The test compares the normal and enlarged first-row heights, then requires each full Traditional Chinese label in the accessibility button hierarchy, access to both ends of every row, a visible tap area, correct editable draft, and no overlap or loss of the draft and voice controls. It runs the system clipped-text accessibility audit without filtering issues. A row may be taller than the viewport at this size; both ends still must be reachable. Existing `AppLanguageUITests/testStoreExamplesFillDraftInEveryLanguageWithoutSending` covers the six labels and taps in all three iOS languages, and `ChatVoiceUITests` covers the voice control's synthetic accessibility activation separately.

The first CI run that reached the method (PR #33, run `43364763538`, iOS 18.5) failed at its first composer check on both phones, before any example was tapped. The app's XCTest log shows the draft in its slot but the microphone button at 67 × 83 pt instead of 40 × 40: on iPhone SE (3rd generation) it ran from y 593.5 to 676.5 on a 667 pt screen, and on iPhone 16 Pro Max its left edge (x 324.7) lay inside the draft (to x 334). The input bar now keeps fixed 40 pt control slots, like the Play build's 40 dp buttons: the microphone takes exactly its slot, and the attach and stop glyphs stop growing at the largest standard text size. At accessibility text sizes the draft shows three lines before it scrolls instead of five: one 53 pt line already makes the field 64 pt tall, so five would make the input bar about 350 pt, over half of the iPhone SE screen, and with the fixture's three-line notice the conversation would keep less than the method's 80 pt of scrolling space. These changes still need the simulator run.

Neither XCTest's accessibility hierarchy nor a synthetic control activation proves actual VoiceOver focus order, gestures, announcements, or speech. After simulator execution, also test real VoiceOver and a system-selected accessibility text size on an appropriately isolated iOS simulator or device, including all six rows, scrolling in both directions and the microphone, without live model or microphone input. No native result is claimed by this document.

## Composer behavior still different from Android

The APK resource evidence records `想聊什麼，或需要幫忙查找什麼？`, `補充或改要求…`, `回答渥屋助理的問題`, and `按住說話，點一下打字`. Resource inspection alone cannot establish when they appear. The Android `420b1d26` source chooses placeholders by voice-controller presence, composer mode, history, and conversion state. iOS retains the first-message text-field placeholder `輸入訊息` / `输入消息` / `Type a message`; the store's empty prompt is not yet used there. For existing messages iOS uses `繼續說點什麼…` / `继续说点什么…` / `Say something more…` when the field is empty.

On iOS the separate microphone button receives the hold or accessible activation, rather than the text field. The voice controller may be unavailable or disabled by settings. While `isSubmitting`, the actual draft and microphone controls are disabled, and Cancel is available: this candidate does not implement Android's typed or voice interruption and must not display an instruction suggesting it does. iOS tool approval sheets likewise are not the Android composer `Answer` mode; that mode and its response semantics remain unimplemented. Existing voice settings and lifecycle behavior are unchanged.

`ChatStreamingUITests/testComposerIdleAndBusyControlsInThreeLanguages` uses the real iOS composer and isolated cancellable synthetic model to check the initial placeholder and microphone label in all three languages, disabled input and microphone during generation, enabled Cancel, then restored controls and draft after cancellation. It does not claim a live model, voice recognition, Android runtime, or actual VoiceOver test. It belongs to `ui-startup` and remains pending native execution.
